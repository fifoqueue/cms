# SSO (OpenID Connect)

상위 문서: [AGENTS.md](../../AGENTS.md)

OIDC Authorization Code + PKCE를 사용합니다. **설정 → 싱글 사인온**에서 켭니다(제공자 주소, 클라이언트 ID·비밀(봉인 저장), 인증 방식, 스코프, 연결 없이 허용할 주체). 관리 화면에서 설정하는 제공자의 리디렉션 URI는 기존과 같은 SEO 사이트 주소 + `/admin/sso/callback`이며 화면에 표시됩니다. 로그인·초대 연결·계정 연결 모두 이 URI를 유지하므로 업그레이드 시 IdP 등록 주소를 바꿀 필요가 없습니다. 환경변수로 고정한 제공자는 `OIDC_REDIRECT_URI`를 그대로 사용합니다. 플러그인 로그인 메서드의 `callbackUrl`은 `/admin/sign-in/callback`입니다. 두 웹 콜백은 같은 흐름을 처리합니다. 환경변수는 관리자 설정보다 우선합니다(`OIDC_ISSUER`, `OIDC_CLIENT_ID`, `OIDC_REDIRECT_URI`가 **모두** 있어야 하고 일부만 있으면 시작 시 설정 오류). 비밀 값은 API 서버에만 있습니다.

| 변수                                | 설명                                                                                                  |
| ----------------------------------- | ----------------------------------------------------------------------------------------------------- |
| `OIDC_ISSUER`                       | 제공자 issuer (https, 쿼리 없음)                                                                      |
| `OIDC_CLIENT_ID`                    | 클라이언트 ID                                                                                         |
| `OIDC_REDIRECT_URI`                 | 웹 앱의 `/admin/sso/callback` URL (제공자에 등록)                                                     |
| `OIDC_CLIENT_SECRET`                | 클라이언트 비밀. `OIDC_CLIENT_AUTH_METHOD`가 `none`이 아니면 필수                                     |
| `OIDC_CLIENT_AUTH_METHOD`           | `client_secret_basic`(비밀이 있을 때 기본) · `client_secret_post` · `none`(PKCE만)                    |
| `OIDC_SCOPES`                       | 공백 구분, 기본 `openid` (반드시 포함)                                                                |
| `OIDC_NAME`                         | 로그인 버튼 표시 이름 (기본 `SSO`, 최대 64자)                                                         |
| `CMS_ALLOW_PASSWORD_LOGIN`          | Boolean, default false. Emergency override forcing password sign-in on without changing stored policy |
| `OIDC_ALLOWED_SUBJECTS`             | JSON `{ "<subject>": "<기존 관리자 이메일>" }` — 연결 없이 로그인할 수 있는 주체 목록                 |
| `OIDC_FRONTEND_SECRET`              | `CMS_FRONTEND_SECRET`의 옛 이름(선택). 없으면 자동 연결된 비밀을 씁니다                               |
| `OIDC_MAX_PENDING_REQUESTS`         | 대기 중 인증 요청 수 전체 상한. 기본 1000, 범위 1–100000                                              |
| `OIDC_MAX_PENDING_PER_CLIENT`       | 클라이언트 하나의 대기 요청 상한. 기본 10, 전체 상한 이하                                             |
| `OIDC_STARTS_PER_MINUTE`            | 분당 SSO 시작 수 전체 상한(**API 프로세스마다**). 기본 300                                            |
| `OIDC_STARTS_PER_MINUTE_PER_CLIENT` | 클라이언트 하나의 분당 SSO 시작 수(프로세스마다). 기본 10, 전체 이하                                  |

- 계정은 **제공자의 이메일 클레임으로 절대 자동 연결하지 않습니다.** 기존 사용자와의 연결은 로그인한 상태에서 `start`(연결) → `callback`으로 명시적으로 `issuer`+`subject`를 묶거나, 운영자가 제공자별 허용 목록에 직접 등록한 주체만 가능합니다. 초대·재설정 토큰 소유자는 아래 `claim` 흐름으로 연결할 수 있습니다.
- Store `sso` as `{ settings: { providers }, secrets: { [providerId]: sealedSecret } }`. Legacy single-provider settings read as provider `default`. The old `passwordLogin: false` migrates to Settings → Sign-in's `methods: ['sso']` before an SSO save removes the field. Incoming optional `passwordLogin` is accepted and ignored for one release; outputs omit it and `passwordLoginForced`. Provider clients are cached independently. `OIDC_*` replaces only the provider list with `environment`. Administrator DTOs expose only `clientSecretConfigured`, never secrets.
- Retaining an omitted secret also requires an equivalent issuer URL. A changed issuer without a newly supplied secret is rejected at `providers.<index>.clientSecret`. Provider binding and policy matching compare `new URL(issuer).href` (including the root trailing-slash equivalence); stored verified `iss` and subject bytes remain exact.
- The `sso` engine method lists enabled providers, redirects to the selected provider and verifies its callback query with server-kept OIDC checks. Setup uses an invitation/reset token and commits the identity claim with token consumption, then applies the engine's sign-in/factor policy. Expired/used tokens and allowlisted subjects cannot claim. SSO `/start` and `/callback` HTTP routes now accept only authenticated account linking; legacy login/claim requests return 409 directing clients to the step flow.
- A successful claim deletes all of that user's outstanding reset/invite tokens in the same transaction. Claim refuses replacement of an existing link for the issuer; authenticated account linking remains the replacement flow. The migration's `provider_id` defaults to `default`.
- Allowed primary methods belong only to Settings → Sign-in. Password exclusion blocks password login, public forgot-password requests and password selection by link. Invitation/administrator-reset emails keep `/admin/password?token=…` but ask the recipient to set up sign-in. `CMS_ALLOW_PASSWORD_LOGIN` adds password to the effective methods and is exposed as `passwordForced` by the sign-in settings DTO.
- Provider edits and unlink-last checks share the sign-in policy's `signIn.admission` row lock and scoped DB transaction. Without another allowed, ready method usable by the acting user, provider edits must retain the user's linked/assigned access, and unlink cannot remove the last matching identity unless an assignment remains. A temporary runtime password fallback is not an explicitly allowed alternative when restoring providers. Access issues use `providers`; missing secrets use `providers.<index>.clientSecret`.
- Recovery codes require current `settings.manage`: generating replaces the set with ten 80-bit codes, returned only once; only digests are stored. Input is case-insensitive with optional hyphens. Recovery uses login protection/visitor headers, consumes once under concurrency, issues a session without identity binding and logs a warning. Email-enabled sites notify on generation and use (remaining count). Privacy export includes only code metadata; erasure removes the codes.
- Generation additionally requires a non-expired interactive session issued within ten minutes; API tokens are refused. Recovery performs capability resolution and a consume attempt even for missing/ineligible accounts (using a dummy user id for consumption). Notification failures are logged without losing generated codes or denying an otherwise successful session. Password resets/changes and administrator sign-out-everywhere delete recovery codes transactionally.
- `20261109000000_sso_providers_recovery` discards only pending SSO requests, adds provider/claim fields and recovery codes, and replaces the single-user identity index with `(user_id, issuer)`. Existing identity bytes, ids and bound sessions survive. Generate and validate Prisma before deployment; do not run older single-provider writers after migration.
- 인증 상태(`state`, `nonce`, PKCE verifier)는 서버의 `sso_transactions`에만 있으며 1회용이고 10분 뒤 만료됩니다. 브라우저에는 핸들만 전달됩니다.
- **정확한 식별자 비교**: `issuer`·`subject`는 `user_identities`에 UTF-8 바이트(`VARBINARY(255)`)로 저장되고 유일 인덱스도 바이트 단위입니다. 대소문자 접기·정규화·후행 공백 무시가 없으므로 `Alice`와 `alice`는 다른 계정입니다. 도메인은 조회 결과의 값이 검증된 값과 정확히 같을 때만 받아들이고, 올바른 유니코드가 아니거나 255바이트를 넘는 값은 거부합니다. 이 컬럼을 텍스트 콜레이션으로 바꾸지 마세요.
- **세션 폐기**: 연결(`user_identities`)마다 불변 `id`가 있고, 연결을 통해 발급한 세션은 `sessions.identity_id`(FK, `ON DELETE CASCADE`)로 묶입니다. 연결 해제나 다른 계정으로 교체하면 DB가 같은 문장에서 그 세션들을 지웁니다. 해제와 경합한 로그인은 FK 위반으로 거부되어(401) 세션이 남지 않습니다. 비밀번호 세션은 영향받지 않습니다. 관리자 Account 화면에서 연결·해제할 수 있습니다.
- 운영자 할당(`OIDC_ALLOWED_SUBJECTS`)으로 로그인한 세션은 연결에 묶이지 않습니다. 할당을 지우고 재시작하면 새 로그인은 막히지만, 기존 세션은 만료(`SESSION_TTL_HOURS`)나 로그아웃까지 유지됩니다.
- **시작 속도 제한(먼저 검사)**: `start`는 제공자 호출·DB 접근 전에 `RateLimiter`(`domain/ports.ts`)로 클라이언트별·전체 속도를 동기적으로 예약합니다. 초과하면 429 `rate_limited`이며 그 요청은 아무 작업도 하지 않습니다. 구현 `infra/memory-rate-limiter.ts`는 프로세스 메모리의 토큰 버킷(창 60초)이라 **API 인스턴스마다 따로** 셉니다. 인스턴스가 N개면 실제 허용량은 최대 N배이고, 재시작하면 초기화됩니다. 키는 허용된 시도 뒤에만 기억하고 마지막 허용 후 한 창이 지나면 잊으므로, 기억하는 키는 최대 전체 한도의 2배입니다.
- **요청 등록 상한(프로세스 간)**: 속도 제한을 통과한 등록은 DB 트랜잭션과 공통 행 잠금(`settings`의 `sso.admission`)으로 직렬화해 모든 인스턴스를 합쳐 전체 상한과 클라이언트별 상한을 함께 지킵니다. 만료 요청은 다음 등록 시 정리합니다. 상한에 도달하면 SSO 시작만 409로 거부되고 비밀번호 로그인은 유지됩니다.
- **클라이언트 식별**: API는 웹 서버만 보므로 방문자 주소는 웹 서버가 증명합니다. 웹은 보호되는 요청(로그인·비밀번호 재설정·댓글·SSO 시작)에 `getClientAddress()`(adapter-node의 프록시 설정 `ADDRESS_HEADER`/`XFF_DEPTH`를 따름)와 프런트엔드 비밀을 `x-cms-client-address`/`x-cms-frontend-secret` 헤더로 보냅니다. API는 비밀이 일치할 때만(상수 시간 비교) 주소를 믿고 IPv4 주소 또는 IPv6 /64 단위로 셉니다. 비밀이 없거나 틀린 요청(API 직접 호출 포함)은 주장한 주소와 무관하게 하나의 공용 할당량과 속도를 나눠 씁니다. 연결 요청은 사용자 단위로 셉니다. 속도 제한과 등록 상한은 같은 클라이언트 키를 씁니다. 여러 주소를 가진 공격자는 전체 상한까지 채울 수 있습니다.
- 라우트 파일: `http/routes/api/v1/auth/sso/{index,start,callback,identity}.ts`, `admin/sso.ts`, 서비스: `domain/auth/sso-service.ts`, 설정: `domain/auth/sso-settings.ts`, 클라이언트 식별: `http/client-identity.ts`.
- 마이그레이션 `20261023000000_sso_exact_identity_sessions`는 적용 시 **모든 세션과 대기 중 SSO 요청을 삭제**합니다(모두 다시 로그인). 계정·연결·콘텐츠·플러그인은 유지됩니다. 적용 전에 DB를 백업하세요.
