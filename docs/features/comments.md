# 댓글

상위 문서: [AGENTS.md](../../AGENTS.md)

- Authenticated moderators bypass plugin comment checkers and start approved; `comment.beforeSave` still runs. Notification recipients are fixed by core: `comment.notification` may change only subject and text, not `to`.

- Password-protected entries require the existing `x-cms-unlock` proofs for comment reads and submissions. Locked entries do not render comments; recent-comment widgets exclude protected entries.
- Public comment submissions accept an optional bearer session. A verified user's `userId`, name and email come from the profile, never the submitted identity. Discussion `requireLogin` rejects anonymous submissions; moderators still use the moderation capability.
- Discussion `showName`, `showEmail`, and `showWebsite` independently remove anonymous identity fields (all default on). Disabling names requires a nonempty `defaultName` (max 100); disabled submitted values are ignored before validation. Authenticated comments always use the profile name/email and no submitted website. Missing anonymous email is stored as an empty string, never grants known-commenter status or a commenter proof, and has no avatar. Moderators with resolved `comments.moderate` bypass built-in approval rules, including word lists and link limits. Captcha, rate limits, honeypot, protected/open/reply checks and plugin verdicts still apply; submitted role/capability fields never grant this exemption.
- Public comment pages expose only the three form-field flags in `fields`. SvelteKit enhances the comment action without a document navigation or whole-page invalidation: it refreshes the returned thread page/count/pending receipt, preserves failed drafts/reply context, prevents concurrent submissions, and resets captcha tokens after every attempt. Ordinary forms keep the POST/redirect fallback. Remembered preferences contain only enabled fields; preference/proof cookies remain explicit opt-in.
- `GET /api/v1/comments` returns `viewer` (name only), `requireLogin`, and `ownPending`. `x-cms-comment-pending` carries a signed, entry-bound, 24-hour receipt; only that receipt's currently pending comment is shown. Spam/trash and other pending comments remain hidden. Comment responses use `private, no-store`.
- Submission returns `{ status, comment, page, pendingProof, commenterProof }`; `page` identifies the top-level thread's page, including replies. The web keeps `cpage` and failed reply context, and stores receipts in httpOnly cookies. Commenter name/email/website and the signed one-year commenter proof are remembered only after an explicit checkbox opt-in; later submissions carry it in `x-cms-commenter-proof`. `known` moderation accepts that proof only while its referenced comment remains approved for the same email; the unsigned preference cookie is never identity. All session, unlock, pending-receipt and commenter-preference responses use `private, no-store`.
- Discussion `showAvatars` defaults off; when enabled `avatarDefault` selects the Gravatar fallback style. Public DTOs contain only a signed same-origin avatar proxy URL, never an email or public email digest. Admin comment DTOs include `parentAuthor` for reply context; moderation supports a `contentId` filter.

- Comments are core: plain-text bodies, threaded up to the configured depth, paginated by top-level comment. Public DTOs never contain email addresses. `contents.comment_count` counts approved comments and is updated in the same transaction as every status change.
- Public entry pages let viewers with `comments.moderate` approve, unapprove, trash and permanently delete comments in place. A separate `management` projection contains only display fields, is paged per entry (`mstatus`/`mpage`, 20 rows), and is never sent to non-moderators or for locked entries. These responses are `private, no-store`. The `moderateComment` action resolves the entry from the request address and passes `contentId` to the bulk API, which checks every comment belongs to that entry before mutating anything. Permanent deletion requires `confirm=delete`; enhanced actions preserve the draft, and ordinary forms show scoped failures or an allowlisted `commentNotice` after redirect. A failed refresh never changes a successful mutation into a retryable failure.
- Submission order: validation, rate limit/captcha, honeypot (accepted silently, stored nowhere), open check (discussion on, type supports comments, entry allows them, age limit), reply check, block/hold words and link limit, moderation mode (`manual`, `known`, `auto`), `comment.beforeSave` filter (only `body` and `status` are taken), insert, hooks, notification mail (queued). Held and spam comments both answer `pending`.

## Notifications (email and browser push)

- **Claim (request path).** When a comment becomes approved (submitted approved, approved by edit/bulk moderation, or a moderator reply), one transaction sets `comments.notified_at` only while the row is approved, not erased and not yet announced, and inserts a sealed `comment.notice` job. Nothing else runs in the request. A failure rolls both back and surfaces to the caller; edit/bulk approval claim every approved row they touch (a no-op once claimed), so repeating a failed approval announces it. A concurrent unapprove/spam either commits first (no claim, no job) or after; then the job finds the comment not approved and clears `notified_at` (only while it is still not approved), so a later approval announces it once. Comments approved before the `20261115000000_comment_notifications` migration count as announced. Lock order for every comment writer is entry, then comments: moderation (status, edit, delete) reads the comments' entries before its transaction and then takes only locking reads (entries, then comments, in id order) before plain writes, the claim locks the entry before its conditional UPDATE, inserts lock the entry first, and deleting entries (one entry, or a deleted user's entries without reassignment) locks them right after the permalink lock and removes their comments before the entries (`deleteEntries`) (InnoDB cannot cascade into replies, whose `parent_id` SET NULL re-checks the entry being deleted). No moderation write therefore fails MariaDB's snapshot check (1020) or deadlocks (1213) against a claim or an entry deletion.
- **Fan-out and delivery (jobs, retried with the job runner's backoff).** `comment.notice` resolves recipients from current data and, in one transaction keyed `notice:<commentId>` (`notice_dispatches`, kept 30 days), counts each recipient in its flood window and queues one `comment.mail` per mail recipient and one `comment.push` per distinct browser (registrations reached through the parent comment and its user are deduplicated by exact endpoint), or the window's `comment.summary`. A retried fan-out queues nothing twice. Under the `privacy.jobs` lock (the one erasure scans jobs under), the fan-out and summary collection re-check every job's subjects and skip any naming an erased comment or user (an erased recipient is not counted; an erased summary's held count is dropped). `comment.mail` and `comment.push` re-check eligibility right before sending (channel setting and email delivery on, the recipient still has that address, reply mail not unsubscribed, registration still active, and — except for summaries — the announced comment, whose id each job carries, still approved and not erased); an ineligible notice is dropped and logged at info as `Comment notification dropped` with `{ channel, reason: disabled | recipient | unsubscribed | withdrawn, notices }` (`withdrawn`: the comment was unapproved, trashed, deleted or erased). Copy is rendered (site language) and filtered when sent; transport failures retry. Moderator mail about held comments still uses `EmailService.queue`.
- **Who.** The entry's author (email under `notifyAuthors`, push to their registered browsers under `pushNotifications`) and, for a reply, the parent comment's author. Reply email needs no visitor opt-in: it is sent when `notifyCommenters` is on, email delivery is enabled, the site address is set and the parent has an email. Reply push goes to the registrations of the parent comment and, if the parent was written signed in, of that user. Nobody is notified about their own comment (same email or same userId), spam/pending/trash never notify, and replies to a non-approved parent notify only the entry's author. When the entry's author is the parent author they get the reply notice only.
- **Public page.** `notifications.email` says replies to the viewer's comment will be emailed (setting on, email enabled, site address set, email field shown or viewer signed in); `notifications.push` is the VAPID public key while push is offered. A submission answers `pushToken` (signed, bound to the new comment, one hour; issued for every verdict so it reveals none) that `POST /api/v1/comments/push` exchanges for a registration. Disabled push or a spam/trashed comment is accepted silently.
- **Registrations** (`push_subscriptions`): one per owner (comment or user) and endpoint (compared by SHA-256, exact bytes); at most 5 per comment and 10 per user, the least recently seen beyond the cap is deleted. `expirationTime` is stored. Endpoints must pass `isPushEndpoint` (`PUSH_SERVICE_HOSTS`, https, port 443, no credentials/fragment) at registration (field issue `subscription.endpoint`, `CommentPushEndpointInvalid`) and again before every send. Registration, renewal, unsubscribe and the writer's own registration writes share a fixed 20 per 10 minutes limit per proven client (unproven callers share one bucket) or per user.
- **Renewal.** `POST /api/v1/push/renew { old: { endpoint, auth }, subscription }` moves active rows whose endpoint matches exactly and whose stored `keys.auth` equals `old.auth` (constant-time); unknown endpoints and wrong secrets answer the same `{ ok: true }` and change nothing. Pages store `{ endpoint, auth }` of the last registered subscription (`cms_push_subscription`; the old endpoint-only `cms_push_endpoint` is discarded and the current subscription becomes the baseline) and renew at most once a day per device: a replaced subscription moves its registrations, an unchanged one is renewed with itself as `old`, which refreshes `last_seen_at` so regular visitors never go stale. The worker's `pushsubscriptionchange` sends `oldSubscription`'s endpoint and `getKey('auth')`, and skips renewal when that key is unavailable.
- **Validity.** Web Push has no silent probe (`userVisibleOnly`), so validity signals are: the client's re-sync and `pushsubscriptionchange` (renewal refreshes `last_seen_at`), and send results (404/410 → `gone`, 401/403 → `rejected`; 429/5xx retry with the job backoff; other answers and 3xx drop the message). A daily task (`comments.push-validate`) invalidates rows whose `expirationTime` passed (`expired`), whose endpoint fails the allowlist (`endpoint`) or that were not renewed for 120 days (`stale`). Invalid rows are kept with `invalid_reason`/`invalidated_at` and deleted after 30 days. Unsubscribing deletes at once.
- **Content.** Mail passes the `comment.notification` filter (subject/text only, never `to`) and is sent by `EmailService.sendNow` inside its job; pushes (TTL 1 day, urgency normal) carry a payload `{ title, body, url, tag, icon? }` passes the `comment.push` filter (only `title`/`body` may change). `url` is `${siteUrl}${path}#comment-<id>`, `body` a plain excerpt of at most 140 characters, `icon` the same-origin site icon when set, and `tag` is stable per thread (`entry-<contentId>` for authors, `comment-<parentId>` for replies) so bursts replace each other; the title adds "+N more" / "외 N개" for earlier pushes in that tag within the last hour.
- **Floods** (constants in `comment-notifier.ts`): normal use delivers every notice. Per recipient and channel (email address; push user or parent comment), past `NOTICE_FLOOD_LIMIT` = 30 notices in `NOTICE_FLOOD_WINDOW_MS` = 1 hour the rest are held and one summary ("N new comments" / "새 댓글 N개", linking to the entry for replies or the comment list for authors) is sent when the window ends; nothing is dropped. Counters live in `notice_windows` keyed by the SHA-256 of the recipient key. At the window's end `comment.summary` moves the held count into one durable summary delivery in the same transaction (a failure keeps the count for the retry); a summary whose channel is off by then is dropped and logged with its count.
- **Unsubscribe.** Reply emails end with `${siteUrl}/comments/unsubscribe?token=…` (signed `email.<commentId>.<expires>.<sig>`, 180 days); `POST /api/v1/comments/unsubscribe` stops reply mail for that comment (`comments.reply_mail`). Push tokens (`push.<registrationId>…`) delete a registration. Invalid, tampered or expired tokens answer `invalid_input` `CommentUnsubscribeInvalid`; repeating a valid one succeeds. `EmailMessage` has no header support, so no `List-Unsubscribe` header is sent.
- **Privacy.** Registrations are deleted with their comment or user (cascade) and by personal-data erasure; export lists them (`pushSubscriptions`: id, comment, push service host, status, dates — never the endpoint capability). Queued push and summary jobs carry the comment/user/email subjects, so erasure removes them.

- Moderators (`comments.moderate`) approve, unapprove, mark spam, trash, delete, edit and reply (replying approves the parent). Deleting a comment moves its replies up. Spam and trash older than 30 days are purged by a task.

## Author IP address and user agent

- Like WordPress `comment_author_IP` / `comment_agent`, each comment stores `comments.author_ip` (`VARCHAR(45)`, canonical text: dotted IPv4, IPv4-mapped IPv6 as IPv4, other IPv6 in RFC 5952 form, no zone) and `comments.author_user_agent` (`VARCHAR(255)`). Both are null when unknown; comments written before `20261117000000_comment_author_meta` have none.
- Only the web server can vouch for them: the API takes the address from `SSO_CLIENT_ADDRESS_HEADER` and the browser's `User-Agent` from `CLIENT_USER_AGENT_HEADER` (`x-cms-client-user-agent`, SDK `ClientProof.userAgent`) only when the request carries the valid `SSO_FRONTEND_SECRET_HEADER` (`ClientResolver.address` / `userAgent`). Without it, or with a wrong secret, both are null whatever the headers claim. The user agent loses control characters, is trimmed and cut to 255 characters. Visitor submissions and moderator replies (the moderator's own request; SDK `comments.reply(id, body, proof)`) store them; admin edits never change them.
- They are moderator data: admin DTOs (`authorIp`, `authorUserAgent`) only. Public comment DTOs, pages, `ownPending`, the `management` projection's display fields, feeds, recent-comment widgets, `comment.public`, notification mail/push and webhook deliveries never carry them. `GET /api/v1/admin/comments` `search` also matches the IP address, and `ids` (up to 100 comma-separated ids, deduplicated, each at most 36 characters, combined with the other criteria) lets a moderator's public thread page fetch metadata for exactly its visible comments.
- Plugins receive them as WordPress plugins do (antispam services such as Akismet need them to check and to report spam/ham): `PluginComment` (`comment.created/statusChanged/updated/deleted`), `CommentCheck.comment` (`commentCheckers`) and the `comment.beforeSave` draft (read-only there; only `body` and `status` are taken). This is the existing plugin trust model — every activated plugin is administrator-installed trusted server code whose `hooks` already see the private `authorEmail`; there is no per-field gate, so a plugin must keep them out of public output and show them only to users with `comments.moderate` (its `access: 'admin'` routes require `plugins.manage`; admin pages take a `capability`). Webhooks (`tools.manage`, not `comments.moderate`) get comment events without them.
- WXR: import reads `wp:comment_author_IP` (kept only when it is a valid IP address, canonicalized) and `wp:comment_agent` (cleaned like the header); export writes both only when the exporting user also has `comments.moderate` (export itself needs `tools.manage`), otherwise the tags are omitted. Personal-data export lists them with the commenter's comments; erasure sets both to null with the other personal fields.
- Retention: there is no separate expiry. IP address and user agent persist with their comment until it is deleted — by a moderator, with its entry, or by the purge of spam and trash older than `COMMENT_PURGE_DAYS` (30) days — or until the commenter's personal data is erased.
