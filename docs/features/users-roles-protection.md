# 사용자·역할·보호

상위 문서: [AGENTS.md](../../AGENTS.md)

- Saving captcha settings rejects providers absent from the active registry. Changing provider clears the old secret unless a replacement is explicitly submitted; re-enter the new provider's secret before enabling verification. Unchanged providers retain an omitted secret.
- Public registration stops before plugin hooks when membership is closed. Otherwise rate-limit/captcha protection runs before the deny-only `user.registrationAllowed` filter. Moderator notification capabilities resolve with each recipient's user id.

- Plugin role defaults are assignable while registered; saved administrator definitions override defaults. Withdrawing a default does not delete accounts. Unknown roles/capabilities grant no permissions.
- Private profile metadata is stored in `profile-meta.<userId>` settings, validated against active field declarations, and never added to public author DTOs. Writes share `users.lock` with account deletion and erasure. Privacy exports include all stored metadata, even for inactive plugins; core erasure deletes it atomically and refuses subsequent writes to the anonymized account.
- Captcha provider discovery exposes IDs and labels only. Public captcha configuration exposes nullable `widget: { script, scriptOrigin, render, origins, attributes, responseField }`. Scripts are credential-free HTTPS URLs (max 2048); declarations allow 20 `data-*` string attributes (names 80 characters, values 1024), and response fields match `[A-Za-z][A-Za-z0-9_-]*` (max 100). `render` is a dotted function path (up to four identifiers, max 256) called per mount as `fn(container, { sitekey, callback })`; null means auto-render from attributes. The API supplies `data-sitekey` for auto widgets unless explicitly set, allowing one extra public attribute. `origins` contains up to ten HTTPS origins (wildcard subdomains allowed; no paths). Add the API-derived `scriptOrigin` and documented extra hosts to page-local CSP only. Apply attributes through DOM APIs, never HTML; resolve render paths without eval. Core providers use these same descriptors. An omitted widget is null, not a verification bypass; missing/failed verification fails closed. Provider-specific CSP notes and sources are in [extension points](../plugins/extension-points.md#users).

- Roles are WordPress-style (`administrator`, `editor`, `author`, `contributor`) and grant capabilities (`packages/sdk/src/capabilities.ts`, pure and browser-safe). Services authorize with `authorize(actor, capability)`; routes may also pass a capability to `session(app, capability)`. Content rules distinguish own entries (`content.create`/`content.publish`) from others' (`content.editOthers`). At least one administrator always remains (serialized writes). Author choices (`GET /api/v1/admin/users/authors`, `content.editOthers`) are `{ id, name, slug }`; the slug feeds the admin content list's `author` filter.
- Password reset and invitations send single-use tokens by email; API tokens (`cms_pat_…`) authenticate like sessions and are listed/revoked by their owner. Hashes only are stored.
- Administrators (`users.manage`) send a reset link with `POST /api/v1/admin/users/:id/password-reset` (no captcha or visitor limit; 20 per administrator per hour) and sign a user out everywhere with `DELETE /api/v1/admin/users/:id/sessions` (API tokens stay). Bulk role changes use `PUT /api/v1/admin/users/:id/role`, which changes only the role. Users list their own sessions at `GET /api/v1/auth/sessions` (opaque ids derived from the session digest, issue and expiry times) and sign one out with `DELETE /api/v1/auth/sessions/:id`. Custom roles are deleted with `DELETE /api/v1/admin/roles/:key?reassignTo=<role>`, which moves their users first.
- Admin content lists sort by `orderBy` (`updatedAt`, `publishedAt`, `title`, `author`, `commentCount`; an SDK allowlist) and `order`, with id as tie-breaker. The dashboard's box order and hidden boxes follow the authenticated writer across browsers: `GET/PUT /api/v1/admin/dashboard-preferences` reads/writes only `dashboard.<userId>` in core settings, with the owner taken from the session. The strict SDK contract accepts only `order` and `hidden`, each at most 100 identifiers of 1–200 characters. The enhanced Screen Options form reports saved/errors; the former shared `cms_dashboard` cookie is ignored rather than assigned to an account. Plugin boxes come from `GET /api/v1/admin/dashboard-widgets`.
- `ProtectionService` guards sign-in, password reset, comments and protected-content unlock: DB-backed rate limits (`rate_limit_buckets`, shared by all instances) and captcha (Turnstile, hCaptcha, reCAPTCHA; secrets sealed). An attempt atomically reserves its counters before password, mail or comment work. Unproven visitors share one visitor bucket, so direct API calls cannot bypass the client limit by changing account names. `captcha_required` (403) asks the form for a captcha.
- Password changes and resets atomically update the hash and revoke reset links, other sessions and API tokens. Reset tokens are checked before password hashing and consumed in the same transaction as the credential change.
- Secrets stored in settings (SMTP password, captcha and Meilisearch keys, webhook secrets) are sealed with `SecretBox` (AES-256-GCM, `CMS_SECRET_KEY`) and never returned; admin DTOs expose only `…Configured` flags.
- 모든 웹훅, OIDC, Meilisearch, SMTP, 플러그인 업데이트 및 아바타 HTTP 연결은 DNS 결과를 검사하고 확인한 IP에 고정하는 공용 egress 정책을 통과합니다. 사설망·루프백·링크 로컬은 기본 차단하며 `egress.manage` 권한이 있는 관리자가 설정 → 외부 연결에서 서비스·호스트·포트·IP/CIDR을 함께 허용해야 합니다. 메타데이터·미지정·멀티캐스트·예약 주소는 허용 규칙으로도 열리지 않습니다. `CMS_EGRESS_ALLOWLIST`는 같은 규칙의 관리자 표시용 읽기 전용 재정의입니다. 업그레이드 때 이미 저장된 Meilisearch/SMTP 호스트가 사설 주소라면 현재 해석된 정확한 주소를 한 번만 초기 규칙으로 저장해 기존 로컬 설치를 유지합니다.
